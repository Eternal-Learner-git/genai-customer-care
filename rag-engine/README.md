# RAG/LLM Engine — GenAI Customer Care System

Retrieves relevant policy information and generates a suggested response to
a customer complaint. This is the component that fills in the
`suggested_response` field on each complaint the backend stores.

## What's included

- **`knowledge_base/`** — 4 sample policy documents (refund, delivery, account security, billing)
- **`ingest.py`** — loads the knowledge base, splits it into chunks, embeds each chunk, and builds a FAISS vector index
- **`retriever.py`** — loads the FAISS index and finds the most relevant chunks for a given complaint
- **`llm.py`** — wraps a small HuggingFace language model (`google/flan-t5-base`) that generates the actual response text
- **`rag_pipeline.py`** — combines retrieval + prompt engineering into one function: `generate_suggested_response(complaint_text)`
- **`test_rag.py`** — runs a few sample complaints through the pipeline so you can see it working end to end

## ⚠️ Important: this uses placeholder e-commerce policy docs

Since this project is actually for the **medical domain**, the 4 `.txt` files in
`knowledge_base/` (refund/delivery/billing/account policies) are stand-ins to prove
the pipeline works - they are **not** what should ship in the final project.

Before this is demo-ready, swap `knowledge_base/` for real medical-domain documents, e.g.:
- Appointment scheduling and cancellation policy
- Prescription refill process
- Insurance/billing FAQ
- Patient data privacy policy
- Emergency vs. non-emergency guidance

The pipeline code itself (`ingest.py`, `retriever.py`, `rag_pipeline.py`) doesn't need
to change at all - just replace the `.txt` files in `knowledge_base/` with medical
content and re-run `python ingest.py` to rebuild the index. The `PROMPT_TEMPLATE` in
`rag_pipeline.py` may be worth revisiting too, since medical response tone/caution
requirements are stricter than general customer service (e.g. never giving a diagnosis,
always deferring urgent symptoms to a real clinician).

## ⚠️ About the LLM choice

`google/flan-t5-base` was chosen because it's small (~250M parameters) and runs on a
normal laptop CPU without a GPU, unlike most modern LLMs. This keeps setup realistic
for a student project, but response quality will be noticeably more basic than a
larger model like Llama or GPT-family models. If your team gets access to a GPU or
an API budget later, swapping the LLM only requires changing `llm.py` - nothing else
in the pipeline depends on which model generates the text.

## Setup

**Use the same Python 3.11 setup you used for the NLP engine** - this stack (torch,
transformers) has the same Python 3.13 compatibility issues you hit before.

1. **Create a virtual environment** inside `rag-engine/` using Python 3.11:
   ```bash
   py -3.11 -m venv venv
   ```
   Activate it (Windows PowerShell): `venv\Scripts\Activate.ps1`

2. **Install dependencies:**
   ```bash
   pip install -r requirements.txt
   ```
   This is another large install (torch + transformers + sentence-transformers) -
   expect it to take several minutes.

3. **Build the FAISS index:**
   ```bash
   python ingest.py
   ```
   This downloads the embedding model (~80MB, one-time) and builds `faiss_index/`
   from the documents in `knowledge_base/`. Re-run this any time you change the
   knowledge base documents.

4. **Test it:**
   ```bash
   python test_rag.py
   ```
   The first run will also download the `flan-t5-base` model (~250MB, one-time).
   You should see 3 sample complaints, each with a generated response and a note
   on how many source chunks were retrieved to ground it.

## Folder structure

```
rag-engine/
├── knowledge_base/          # source documents (SWAP FOR MEDICAL CONTENT - see warning above)
│   ├── refund_policy.txt
│   ├── delivery_policy.txt
│   ├── account_security_policy.txt
│   └── billing_policy.txt
├── ingest.py                  # builds the FAISS index from knowledge_base/
├── retriever.py                 # loads the index, retrieves relevant chunks
├── llm.py                         # wraps the HuggingFace language model
├── rag_pipeline.py                  # generate_suggested_response() - the main entry point
├── test_rag.py                        # quick manual test
├── requirements.txt
└── faiss_index/                        # generated by ingest.py (not committed to git)
```

## Next integration point

Once tested and the knowledge base is swapped to medical content, the backend
engineer needs to call `generate_suggested_response(text)` right after (or alongside)
the NLP engine's classification step in `POST /complaints`, then `PATCH /complaints/{id}`
with the result. That wiring hasn't been done yet - this runs standalone for now.

`faiss_index/` should be added to `.gitignore` in the project root - it's a generated
file, not source code. Each teammate should run `ingest.py` locally after cloning.
